# DEADLINE — Endless Rail Survival

A single-player, 2D infinite side-scrolling survival game in pixel-art style, built with **Vite + React + TypeScript + HTML5 Canvas + Tailwind CSS**.

You play a survivor walking an endless abandoned railway line at night. Zombies spawn off-screen, walk toward you, and try to hit you. You kill them with a pipe, a pistol, or a machine gun, collect materials and ammo from their corpses, and heal by "welding" armor with materials. There are no saves and no checkpoints — you survive until you die, and the distance you covered becomes your score.

**No image files, no audio files.** Every tree, house, zombie, bullet, and sound is generated by code at runtime.

## 1. Run it

```bash
npm install
npm run dev      # start the dev server (Vite)
npm run build    # type-check, then production build into dist/
npm run preview  # serve the production build
```

Requirements: Node 18+ (20+ recommended). There is no backend, no database, no network calls at runtime. The only external request is the Google Fonts stylesheet in `index.html`.

Useful in dev: the engine instance is exposed on `window.__deadline`, so you can cheat from the browser console:

```js
__deadline.player.hp = 9999
__deadline.materials = 999
__deadline.phase            // 'menu' | 'playing' | 'paused' | 'dead'
__deadline.zombies.length
```

## 3. How the game works (player's view)

### The core loop

1. **Walk** along a procedurally generated railway line. The world is infinite in both directions; nothing stops you from going back, but distance is measured by how far you have ever gotten from the start point.
2. **Zombies spawn** just outside the left and right edges of the screen. They idle until they notice you, then chase, wind up, and strike.
3. **Fight**: the pipe is quiet but short-range; guns are strong but loud — firing wakes every idle zombie within 430px. This is the central trade-off of the game.
4. **Loot**: every corpse drops materials (always), sometimes pistol ammo, machine-gun ammo, or a medkit. Pickups are magnetized toward you when you get close.
5. **Spend materials**: 40 materials = +25 condition (health) via "Weld". You cannot weld above max health, and the button is disabled when you can't afford it.
6. **Score**: each kill gives its base points × a combo multiplier. The multiplier is `1 + floor(streak / 3)`, capped at ×5. The streak resets if you don't kill anything for 4.2 seconds.
7. **Difficulty ramps** in two ways:
   - **Time**: a "wave" ticks every 42 seconds. Each wave adds zombies to the field cap and boosts brute/runner spawn chances.
   - **Spawn rate**: the delay between spawns shrinks from ~3.2s toward 0.6s as time passes, and after 45 seconds there is a 35% chance of a double spawn.
8. **Death** is permanent: the run ends, a summary appears, and pressing "Ride again" generates a **new random seed** (new terrain). Nothing carries over.

### The three weapons

| Weapon | Slot | Damage | Cooldown | Ammo | Notes |
|---|---|---|---|---|---|
| Pipe | 1 | 48 | 0.34s | unlimited (∞) | Melee, 34px reach, hits up to 3 zombies per swing, quiet |
| Pistol | 2 | 38 | 0.24s | 120 | Accurate (`spread 0.012`), best while crouched |
| Machine gun | 3 | 15 | 0.075s | 500 | Wide spread, hold to spray, loud |

If a gun's ammo hits zero, the game automatically switches you to the pipe and shows a warning toast.

### The three zombies

| Type | HP | Speed | Damage | Points | Behaviour |
|---|---|---|---|---|---|
| Walker | 60 | 27 px/s | 10 | 100 | Standard. Appears from the start. |
| Runner | 40 | 66 px/s | 8 | 160 | Faster, weaker, crouches slightly. Appears after 22s. |
| Brute | 230 | 21 px/s | 24 | 400 | Big, slow, tanky, hits hard. Appears after 80s, chance grows per wave. |

## 4. How the code works (big picture)

The project is split into two completely separate worlds, and understanding this split is the key to understanding the whole codebase:

```
┌──────────────────────────────────────────────────────────────┐
│  REACT LAYER  (re-renders ~14 times per second)              │
│  App.tsx → GameCanvas.tsx → UIHUD / OverlayScreens /          │
│                             TouchControls / Icons             │
│  Renders DOM + Tailwind: health pips, score, buttons, menus   │
│  Reads a plain data snapshot: HudState                        │
└───────────────────────────▲──────────────────────────────────┘
                            │ getHud()   (plain object, ~20 fields)
┌───────────────────────────┴──────────────────────────────────┐
│  GAME LAYER  (runs 60 times per second, plain TypeScript)     │
│  GameEngine  → simulation: physics, zombies, bullets, loot    │
│  renderGame  → paints the whole scene onto ONE <canvas>       │
│  SoundKit    → synthesizes all audio with WebAudio            │
└──────────────────────────────────────────────────────────────┘
```

Why this design?

- **Canvas for the world, DOM for the UI.** Canvas is fast for hundreds of pixel rectangles and avoids 60fps React re-renders. DOM + Tailwind is far easier for buttons, menus, and responsive layout.
- **The engine does not know React exists.** `GameEngine` is a plain class with mutable fields. React only reads a snapshot (`getHud()`) a few times per second. This keeps the hot loop allocation-light and avoids state-sync bugs.
- **A fixed timestep** means physics behave identically on a 60Hz and a 144Hz monitor.
- **Deterministic procedural generation** means the world does not need to be stored. Given a seed and an `x`, the terrain height and the props are always the same, so chunks can be thrown away and rebuilt with no seams.

## 5. Game loop and time

`src/game/useGameEngine.ts` owns the loop:

```ts
const STEP = 1 / 60
let accumulator = 0

const loop = (now: number) => {
  raf = requestAnimationFrame(loop)
  const raw = Math.min(0.1, Math.max(0, (now - last) / 1000))
  last = now
  accumulator += raw

  // Fixed-step simulation, max 5 catch-up steps per frame.
  let steps = 0
  while (accumulator >= STEP && steps < 5) {
    engine.update(STEP)
    accumulator -= STEP
    steps += 1
  }
  if (steps === 5) accumulator = 0   // tab was backgrounded → drop the backlog

  renderGame(ctx, engine, reducedMotion)

  // HUD is only refreshed every 70ms — React does not need 60fps.
  hudAccumulator += raw
  if (hudAccumulator >= 0.07) {
    hudAccumulator = 0
    setHud(engine.getHud(sound.muted))
  }
}
```

Key points:

- `raw` is clamped to 0.1s so a long stall cannot teleport the player through walls.
- The **accumulator** pattern decouples physics from frame rate: at 144Hz some frames run zero steps, at 30Hz some frames run two.
- The 5-step cap prevents a "spiral of death" (if simulation is slower than real time, the backlog grows forever).
- Visual-only work (rendering, HUD) runs exactly once per frame.
- `prefers-reduced-motion` is read once and re-read on change; it disables camera shake in the renderer.

Two clocks exist inside the engine, and this matters:

| Field | Advances when | Used for |
|---|---|---|
| `engine.time` | always (except paused) | animation, flicker, ambient motion |
| `engine.elapsed` | only while `phase === 'playing'` | waves, difficulty, spawn rate, run timer |

## 6. The coordinate system

The canvas is **480 × 270 logical pixels**, stretched by CSS to whatever the screen allows (`image-rendering: pixelated` keeps it crisp). All game math happens in this small space, which is why the art looks chunky and the numbers are readable.

```
 (0,0) ──────────────────────────────► x  (480)
   │
   │   sky / moon / parallax layers
   │
   │ ───── ground surface ≈ y 194…222 ─────
   │   dirt, ballast, sleepers, rails
   ▼
  y (270)
```

- **+y points down.** That is the canvas convention.
- **`player.y` / `zombie.y` are the FEET position**, not the center. Sprites are drawn upward from that point (negative dy).
- **`player.x` is the center.**
- **World vs screen:** the player lives in world coordinates; the camera translates the canvas with `ctx.translate(-cameraX, 0)`. Mouse aim arrives in screen coordinates and is converted with `worldX = cameraX + input.aimX`.
- `GROUND_BASE = 212` is the average ground height. The noise adds roughly −21 to +8, so the ground wanders gently.
- 1 screen width = `CHUNK_W` = 480 world px. Distance shown in the HUD is `maxProgress / 8`, so "metres" are deliberately much bigger than pixels.

### 7.1 `src/game/constants.ts`

**Every tunable number and color lives here.** Nothing else in the codebase hard-codes gameplay values (a few visual magic numbers are inline in the renderer).

Sections:

- **Canvas & world size**: `VIEW_W = 480`, `VIEW_H = 270`, `CHUNK_W = 480`, `GROUND_BASE = 212`.
- **Physics**: `GRAVITY = 1020`, `PLAYER_SPEED = 104`, `PLAYER_CROUCH_SPEED = 52`, `PLAYER_JUMP = -318`, `PLAYER_W = 12` (negative jump velocity = up, because +y is down).
- **Combat/economy**: `PIPE_RANGE = 34`, `MAX_PARTICLES = 260`, `WELD_COST = 40`, `WELD_AMOUNT = 25`.
- **`PHASE_LABEL`**: display names for the four game phases (`menu → standby`, `playing → in transit`, `paused → held`, `dead → end of line`). Flavour text, currently unused by the UI but handy.
- **`PALETTE`**: the single source of truth for colors. `jacket` is a muted green, `scarf` rust red, `zombieSkin` sickly olive, `eye` red, `amber` the lamp/UI accent, etc. Both the canvas renderer and some DOM bits share this mood.
- **`FONT_CANVAS`**: a font string for canvas text (the in-canvas text is actually a hand-made bitmap font, see `render.ts`).
- **`WEAPONS`**: a `Record<WeaponId, WeaponDef>` — damage, cooldown, starting ammo (`-1` = infinite), projectile speed, spread, knockback, and a tooltip hint. `WEAPON_ORDER` fixes the slot order `pipe, pistol, mg`.
- **`ZOMBIE_STATS`**: same idea for the three zombie types, including `points` (base score) and `deathDuration` (how long the corpse lingers).
- **Spawning**: `SPAWN_MIN_INTERVAL = 0.6`, `ZOMBIE_CAP = 18`.

> Change a number here and the whole game re-balances — this file is the intended knob panel.

### 7.2 `src/game/types.ts`

Pure TypeScript types. No runtime code, so it disappears at build time. It is the contract between the engine, the renderer, and the UI.

Important ones:

| Type | Meaning |
|---|---|
| `GamePhase` | `'menu' \| 'playing' \| 'paused' \| 'dead'` — the single state machine of the app |
| `Player` | position, velocity, size, facing, crouch/ground flags, coyote timer, jump buffer, hp, weapon, ammo map, aim angle, animation timers, invulnerability |
| `Zombie` | same shape plus `type`, `state`, `timer`, `cooldown`, `hasStruck`, per-type stats, `seed` (for visual variation) |
| `Bullet` | current and previous position (`px/py` — used for the tracer and swept collision), velocity, damage, life |
| `Pickup` | kind, position, velocity, value, age, `grounded`, `magnet`, `bob` |
| `Particle` / `FloatText` | short-lived visual effects; both use a `life/maxLife` pair so alpha can fade |
| `Prop` / `TerrainChunk` | scenery description and a 480px slice of it |
| `InputState` | the single mutable object every input handler writes into |
| `HudState` | the snapshot React renders — a flat, serializable object |
| `WeaponDef`, `WeaponHud`, `ZombieStat`, `Toast` | supporting shapes |

A recurring design idea: **the engine stores numbers, not sprites.** A zombie is `{x, y, hp, state, anim, facing, seed}`; the renderer decides what that looks like. That is why there are no assets.

Note on `Player.y`: documented as *feet position*. This single convention prevents a lot of collision math.

### 7.3 `src/game/rng.ts`

Deterministic pseudo-randomness — the backbone of the infinite world.

```ts
export function hashInt(seed: number, n: number): number {
  let h = seed ^ Math.imul(n | 0, 0x27d4eb2d)
  h = Math.imul(h ^ (h >>> 15), 0x85ebca6b)
  h = Math.imul(h ^ (h >>> 13), 0xc2b2ae35)
  return (h ^ (h >>> 16)) >>> 0
}
```

- **`hashInt(seed, n)`** — a 32-bit integer mixer. Pure function: same inputs → same output, forever. This is what makes terrain reproducible without saving anything.
- **`hash01(seed, n)`** — the hash mapped to `[0, 1)`.
- **`hashRange(seed, n, min, max)`** — mapped to a range.
- **`mulberry32(seed)`** — a tiny seeded PRNG returning a `() => number` closure. Used to lay out a chunk's props in a fixed order (several random draws in a row, where each chunk needs its own reproducible sequence).
- **`pick(rand, list)`** — random element helper (currently unused, but exported for convenience).
- **`clamp`** — bounds helper.
- **`randRange`** — *non-deterministic* `Math.random()` version, used for combat feel (spread, particle jitter) where reproducibility does not matter.
- **`newSeed()`** — a fresh 32-bit seed for each run.

Two different random systems on purpose:

| System | Used for | Deterministic? |
|---|---|---|
| `hash*` / `mulberry32` | terrain shape, props, stars, clouds | ✅ yes — required |
| `randRange` / `Math.random` | spread, particles, spawn side, loot rolls | ❌ no — feels better |

### 7.4 `src/game/world.ts`

Generates the endless world. Two exports plus a helper.

**`groundHeightAt(seed, x)` — the terrain function.** Instead of storing a heightmap, the ground is a *pure function of x*:

```ts
const coarse = valueNoise(x / 310, range −15…+7)   // gentle hills
const fine   = valueNoise(x / 61,  range −2.6…+2.6) // small bumps
return GROUND_BASE + coarse + fine
```

Each layer is 1D **value noise with smoothstep interpolation** (`t*t*(3-2t)`), which gives soft, walkable slopes instead of jagged randomness. Because the function is stateless:

- Chunks can be unloaded and regenerated with zero seams.
- The player, zombies, pickups, and the renderer can all ask "how high is the ground at x?" at any time, cheaply and consistently.
- Two runs with the same seed are pixel-identical.

**`generateChunk(seed, index)`** builds one 480px slice of scenery:

- Seeds a `mulberry32` from `hashInt(seed, index * 131 + 17)`.
- **Chunk 0 and 1 are hand-authored** (`index === 0`, `index === 1`) so the opening frame always reads clearly: lamp, pines, house, fence, sign near the spawn.
- **All other chunks are procedural** with probability rolls: houses (~54%), lamps (78% + 58%), 1–3 trees, fences, signs, bushes, rocks, plus rare carriage (~10%) and water tower (~5.5%).
- Every prop gets a `depth` (`back` / `mid` / `front`) which controls *draw order*, not distance.
- Props are sorted by `PROP_ORDER` (carriage → waterTower → house → deadTree → pine → bush → fence → sign → lamp → rock) and then by x. This guarantees a stable layered look regardless of insertion order.

**`findLamps(chunks, seed)`** collects lamp positions so the renderer *could* batch warm ground pools. (The renderer currently loops lamps itself; this helper is available if you want to optimize.)

### 7.5 `src/game/engine.ts`

The heart of the game — 1177 lines, zero rendering, zero React. It is a class with public mutable state and private helpers.

#### Fields (state)

```
phase, seed, player, zombies[], bullets[], pickups[], particles[], texts[],
chunks: Map<number, TerrainChunk>, input,
cameraX, shake, flash, elapsed, time, wave,
score, kills, materials, combo, comboTimer, bestMultiplier,
maxProgress, startX, spawnTimer, toast, weldCooldown
```

#### Construction & reset

```ts
constructor() { this.reset('menu', newSeed()) }

reset(phase, seed) {
  // wipe every array, reset stats, place the player on the ground,
  // cameraX = PLAYER_START_X - 190, spawnTimer = 4.2 (grace period)
  this.ensureChunks()
}
```

`reset()` is the single "new game" path — used for the menu background, for `startRun()`, and for `toMenu()`. Because it re-generates the seed and the chunks, going back to the menu gives you a different diorama behind the title.

#### Public API used by React

| Method | Effect |
|---|---|
| `startRun()` | unlock audio, reset with a **new** seed, phase → `playing`, start with the pipe, toast |
| `toMenu()` | reset with a new seed, phase → `menu` |
| `pause()` / `resume()` | only valid from the matching phase; clears `fire` so you don't shoot on resume |
| `selectWeapon(id)` | ignored outside playing/menu or if already equipped; adds a small 0.12s switch delay |
| `cycleWeapon(dir)` | wraps around `WEAPON_ORDER` |
| `weld()` | cost/cooldown/full-health checks → restore 25 hp, spark particles, toast |
| `getHud(muted)` | builds the `HudState` snapshot React consumes |

`getHud()` is deliberately cheap and returns fresh primitives. Interesting transformation: `seed` is rendered as 6 hex characters (`0x1a2b3c` → `"1A2B3C"`) for the pause/death screens; `distance` is `floor(maxProgress / 8)`.

#### `update(dt)` — the master tick

```ts
const step = clamp(dt, 0, 0.05)     // hard safety clamp
if (this.phase === 'paused') return // pause freezes EVERYTHING

this.time += step
this.shake / this.flash / this.weldCooldown  // decay effects
this.toast?.life -= step

if (phase === 'playing')      this.updatePlaying(step)
else if (phase === 'menu')    this.updateMenu(step)
else if (phase === 'dead')    this.updateAfterDeath(step)

this.updateParticles(step)
this.updateTexts(step)
this.updateCamera(step)             // camera still eases in menu/dead
```

Note that particles and floating text keep animating in every phase except paused — so the menu sparks and the death blood still move.

#### Phase-specific updates

- **`updateMenu(dt)`** — an idle "attract mode": the player stands on the ground, `walkPhase` advances so the scarf sways, and the camera slowly pans with `Math.sin(time * 0.16) * 32`. No input is read.
- **`updateAfterDeath(dt)`** — zombies keep their death animation; the corpse is drawn by the renderer.
- **`updatePlaying(dt)`** — the real order of operations:

```ts
this.updateAim()
this.updatePlayer(dt)
this.updateSpawner(dt)
this.updateZombies(dt)
this.updateBullets(dt)
this.updatePickups(dt)
this.updateCombo(dt)
this.refreshChunks()
this.maxProgress = max(maxProgress, player.x - startX)

const nextWave = 1 + Math.floor(elapsed / 42)
if (nextWave > wave) { wave++; toast; sound; shake; spawnBurst(...) }

if (player.hp <= 0) this.killPlayer()
```

#### Aiming — `updateAim()`

Two modes:

1. **Mouse active** — convert the pointer to world space, compute `atan2` from the shoulder position (`y - h*0.58`), and flip `facing` if the angle is not nearly vertical (so you can shoot behind you).
2. **No mouse (touch / keyboard-only)** — if the fire button is held, find the nearest living zombie within 260px and snap the aim at its chest; otherwise aim horizontally in the facing direction.

The 9px dead zone avoids the arm snapping to a weird angle when the cursor sits on the shoulder.

#### Player physics — `updatePlayer(dt)`

This is a small, complete platformer controller. In order:

1. **Decay timers**: cooldown, attack animation, muzzle flash, recoil, invulnerability, hurt flash, noise.
2. **Crouch**: only on the ground; sets hitbox height `30 → 21`.
3. **Horizontal movement**: `approach(vx, move * speed, accel * dt)` — accelerate toward the target speed rather than setting it, which gives weight. Different accel on ground (1400) vs air (720), and faster braking (1500) when there is no input.
4. **Facing**: only from movement when the mouse is not in use (otherwise the mouse owns facing).
5. **Jump** with two classic forgiveness features:
   - **Jump buffering**: pressing jump 0.12s before landing still jumps.
   - **Coyote time**: you can still jump 0.1s after walking off a ledge.
6. **Variable jump height**: releasing jump while rising fast clamps `vy` to `-110`, so a tap is a short hop and a hold is a full jump.
7. **Integrate & collide with the ground**: gravity → move x → move y → compare against `groundHeightAt(seed, x)`. If below the surface, snap to it and clear `vy`. If you were grounded and the new ground is less than 7px below you, "glue" to it — that prevents micro-hopping down gentle slopes.
8. **Walk cycle**: `walkPhase` advances faster when moving (11), slower when idle (2.2), and at 4 in the air. The renderer reads this phase for leg swing and scarf sway.
9. **Fire** if `input.fire && cooldown <= 0`.
10. Clamp `x` to ±100000 as a sanity guard.

There is **no horizontal collision** — no walls, no platforms. The world is a single continuous walkable line, which is exactly what an endless runner needs.

#### Attacking — `attack()`

**Melee (pipe)** is not a physics shape; it is a cheap directional check:

```ts
const dir = Math.cos(p.aim) >= 0 ? 1 : -1
for (const z of zombies) {
  if (wrong side && |dx| > 8) continue
  if (|dx| > PIPE_RANGE + z.w / 2) continue
  if (not vertically overlapping) continue
  damageZombie(...)   // up to 3 targets, then break
}
```

So the pipe is a 34px box in front of you that cleaves through a small horde. Missing does not cost much — it only adds a tiny bit of `noise`.

**Ranged** (`pistol`, `mg`):

```ts
const spread = weapon.spread
  * (crouching ? 0.4 : 1)      // crouching is more accurate
  * (moving ? 1.5 : 1)         // moving is less accurate
  * (onGround ? 1 : 1.25)      // airborne is less accurate
```

It then spawns a bullet at 12px from the shoulder, consumes one round, sets the muzzle flash and recoil, plays the sound, and emits muzzle sparks plus one ejected casing particle. Finally:

```ts
for (const z of zombies) {
  if (z.state === 'idle' && Math.abs(z.x - p.x) < 430) z.state = 'chase'
}
```

**This is the noise mechanic**: shooting wakes everything nearby. If a gun is empty, the game plays a click, shows a warning, and auto-switches to the pipe.

#### Spawning — `updateSpawner`, `pickZombieType`, `spawnZombie`

- Field cap: `min(18, 3 + wave * 2)`.
- Interval: `max(0.6, 3.2 - elapsed * 0.012) * randRange(0.65, 1.3)`.
- After 45 seconds, a 35% chance to spawn a second zombie immediately.
- Type selection is a probability ladder on a single `Math.random()` roll:
  ```ts
  if (elapsed > 80 && roll < min(0.18, 0.02 + wave * 0.015)) return 'brute'
  if (elapsed > 22 && roll < 0.42) return 'runner'
  return 'walker'
  ```
- Spawn position is just outside the camera, left or right: `cameraX - 42 - rand*40` or `cameraX + VIEW_W + 42 + rand*40`, placed on the terrain with a small speed variation (`randRange(0.9, 1.12)`) so a horde never marches in lockstep.
- `spawnBurst(n)` is used on wave-up (1–4 extra bodies).

#### Zombie AI — `updateZombies(dt)`

A four-state machine per zombie:

```
idle ──(notices player)──► chase ──(close enough)──► attack ──(timer)──► chase
  ▲                                                      │
  └──────────────── all states: hp<=0 ──► die ───────────┘ (removed after deathDuration + 0.4s)
```

- **idle**: drifts to a stop, sways. Notices you if you are within 310px standing or **120px crouching** (crouching is stealthy), or within 470px if `player.noise > 0.9` (i.e. you just fired).
- **chase**: sets `facing`, approaches `speed` with 420 px/s² acceleration. If within ~15px (20 for brutes) horizontally and 26px vertically, switches to attack.
- **attack**: stops, waits a **0.32s wind-up** (your window to step away), then — once — checks reach and applies `damagePlayer`. Below the wind-up the arms are drawn raised, which is the visual telegraph. After 0.85s total it returns to chase with a 0.45s cooldown.
- **die**: decreases `vx` with friction, slides, and stays visible for `deathDuration` (0.9–1.5s) while the renderer squashes and fades it.

After the state machine:

- **Gravity and ground snap** (identical logic to the player, minus jumping).
- **Despawn trick**: if a zombie strays more than 560px outside the camera it gets `hp = -999`, and the filter removes anything `hp <= -900`. Cheap and avoids a separate `alive` flag.
- **Separation pass**: a naive O(n²) loop pushes overlapping zombies apart horizontally so the horde does not collapse into one sprite. With a cap of 18 this is at most ~153 pairs per tick — fine.

#### Damage and death

- **`damageZombie(z, amount, dir, hitX, hitY)`** — subtract hp, flash white for 0.14s, force into `chase` (getting hit aggroes a sleeper), apply knockback, throw blood particles, rate-limit the hit sound to one per 35ms, and on death: increment kills/streak, set score = `points * multiplier`, spew two particle bursts, show floating text, play a sound, and drop loot.
- **`damagePlayer(amount, sourceX)`** — ignores damage while `invuln > 0`; applies hp loss, 0.85s invulnerability, hurt flash, **knockback away from the source**, screen shake, red flash, sound, floating `-N` text, blood. Calls `killPlayer()` at 0 hp.
- **`killPlayer()`** — phase → `dead`, stop firing, big shake/flash, death sound, huge blood burst. The input handlers and the death overlay take over from here.

#### Loot — `dropLoot`, `spawnPickup`, `updatePickups`, `collectPickup`

- Every zombie drops `materials` (1–2; brutes 4–7).
- One extra roll: `< 0.11` pistol ammo (+12), `< 0.17` MG ammo (+32), `< 0.21` medkit (+20).
- Pickups are launched with a small upward/random velocity, bounce on the ground (`vy *= -0.28`), settle when slow, then **magnetize**: after 0.4s, within 74px, they accelerate toward the player at a speed that grows with age.
- Collected within 13px → apply value, floating text, spark burst, sound.
- Uncollected pickups vanish after 40s and blink during the last 5s.

#### Bullets — `updateBullets(dt)`

Bullets are fast, so point-in-rect would tunnel through zombies. Instead each bullet keeps its previous position and the engine runs a **swept segment vs. AABB** test — `segmentHitsRect`, a Liang–Barsky clip:

```ts
segmentHitsRect(b.px, b.py, b.x, b.y,
  z.x - z.w/2 - 1, z.y - z.h - 1,   // top-left of the zombie box
  z.x + z.w/2 + 1, z.y + 1)         // bottom-right
```

On a hit: damage, impact sparks, consume the bullet. On a miss: check the terrain (`y > groundHeightAt(x)` → dirt puff), lifetime (`0.95s`), and camera bounds. Only surviving bullets are kept.

#### Combo — `updateCombo(dt)`

`comboTimer` counts down from 4.2s; when it expires the streak resets. The multiplier is a **getter**:

```ts
get multiplier() { return clamp(1 + Math.floor(this.combo / 3), 1, 5) }
```

So 0–2 kills = ×1, 3–5 = ×2, 6–8 = ×3, 9–11 = ×4, 12+ = ×5.

#### Camera — `updateCamera(dt)`

```ts
let target = player.x - VIEW_W * 0.42 + facing * 12
if (playing) target += clamp((input.aimX - VIEW_W / 2) * 0.08, -24, 24)  // look-ahead toward the cursor
const smooth = 1 - Math.exp(-7.5 * dt)
cameraX += (target - cameraX) * smooth
```

Two details worth stealing for any 2D game:

- The player sits at 42% of the screen width, not 50% — you see more of what is ahead.
- `1 - exp(-k*dt)` is a **frame-rate-independent** easing factor. A naive `lerp(a, b, 0.1)` would be faster at high FPS.

The camera does not move while paused or dead (so the death screen is stable).

#### Chunks — `ensureChunks`, `refreshChunks`

- `ensureChunks()` generates every chunk between `cameraX - 0.75*VIEW_W` and `cameraX + 1.75*VIEW_W`. Because generation is deterministic, "generating" is just calling `generateChunk`.
- `refreshChunks()` deletes chunks further than roughly one screen outside the visible band, keeping the `Map` small (usually 3–5 entries).

This is the whole "infinite world": **a sliding window of deterministic scenery.**

#### Effects — `burst`, `floatText`, `setToast`

- `burst(x, y, count, options)` — the universal particle emitter: random angle, random speed fraction, per-particle jitter, gravity and drag. Used for blood, sparks, dust, casings, landing puffs, muzzle flash.
- Particle count is hard-capped at `MAX_PARTICLES = 260`; the oldest are spliced off.
- `floatText` — world-space text with an upward velocity that eases out, 0.85s life.
- `setToast` — one active toast at a time with a 2.8s life, an incrementing `id` (so React remounts and re-runs the entry animation), and a tone (`info` / `warn` / `good`).

### 7.6 `src/game/render.ts`

1645 lines, all pure drawing. `renderGame(ctx, engine, reducedMotion)` is the only export. Nothing here mutates game state (it only reads), with one exception: `ctx` settings.

#### Pixel utilities

- **`DIGITS` + `drawPixelText`** — a hand-built 3×5 bitmap font for `A–Z`, `0–9`, `+ - . !` and space. Each glyph is five strings of `0`/`1`. `drawPixelText` walks the string and fills 1px rects. This is why damage numbers look like they belong to the same machine as the rest of the art instead of a modern font.
- **`textWidth`** — `(length * 4 - 1) * scale`.
- **`stepCircle`** — a stair-stepped circle made of horizontal bands; used for train wheels.

#### Sky and parallax background

| Function | Parallax | What it draws |
|---|---|---|
| `drawSky` | — | 13 stacked color bands from near-black to a warm rust horizon |
| `drawStars` | `0.015` | 78 deterministic stars with individual twinkle; 2px stars get a cross glint. X wraps with modulo so it is endless |
| `drawMoon` | fixed | Per-row `½·√(r²−dy²)` circle (stepped limb), 3 craters, radial-gradient halo, and a slowly drifting cloud across it |
| `drawClouds` | `0.045` + time drift | 7 layered rectangles per cloud + a dim moonlit rim |
| `drawHorizonHaze` | — | Warm transparency bands, plus a light smear behind the town |
| `drawRidge` ×3 | `0.08`, `0.15`, `0.22` | Silhouette hills from 1D value noise (`ridgeHeight`) |
| `drawPylons` | `0.19` | Telegraph poles with drooping catenary wires |
| `drawTown` | `0.26` | Distant buildings with deterministic lit windows and animated chimney smoke |
| `drawDistantTrees` | `0.44`, `0.63` | Fir silhouettes drawn as a trunk + stacked widening rows |
| `drawForegroundLayer` | `1.16` | Very dark grass/weeds **in front of everything**, moving faster than the world |

`drawForegroundLayer` at parallax **1.16** is a nice trick: faster-than-camera foreground sells depth and hides the bottom edge of the screen.

#### Glow sprite caching

```ts
let glowSprite: HTMLCanvasElement | null = null
function getGlowSprite() { /* build a 96×96 radial gradient once */ }
```

A radial gradient is relatively expensive per call, so the renderer bakes it once into an offscreen canvas and `drawImage`s it (with `globalCompositeOperation = 'lighter'`) for lamps, lit windows, and item glows.

#### Ground

`drawGround(ctx, engine, camX)` paints the rail bed in layers, all sampled from the same `groundHeightAt` function:

1. Fill everything below the ground with dirt (a path built every 3px across the screen).
2. Horizontal dark dirt bands.
3. Embedded stones.
4. A darker lower band at `+44px`.
5. Ballast strip (`+2 … +11`).
6. Gravel speckles.
7. Sleepers every 21px.
8. Steel rails drawn as stepped 8px segments.
9. Puddles (42% of spots), with a lighter reflection line.
10. Surface edge stroke + a 1px dead-grass rim.
11. Grass tufts.

`drawForegroundGrass` adds taller blades *in front* of the characters for depth.

#### Props

Each prop has its own `drawX` function. All of them are `fillRect` compositions, scaled and varied by `prop.seed`/`prop.variant`:

| Function | Notes |
|---|---|
| `drawPine` | 3 stacked conical tiers, trunk, left-edge highlight |
| `drawDeadTree` | 2px trunk + 4 recursive branch strokes |
| `drawHouse` | 4 variants: gabled house (with animated chimney smoke), storefront (awning, sign, lit window), chapel (spire, boarded windows), plain. Lit windows use the cached glow |
| `drawCarriage` | Train car: body, roof, ribs, rust patches, 3–4 lit windows, door, graffiti, 3 stepped wheels |
| `drawWaterTower` | Legs, tank, cap, a tiny red marker |
| `drawLamp` | Pole, head, flickering light + `drawLampGlow` |
| `drawFence` | Picket loop with two rails, two color variants |
| `drawSign` | Post + plate with a deterministic 2-digit number drawn in the pixel font |
| `drawBush` / `drawRock` | Small foreground details |

`drawProp` is the dispatcher: it looks up the ground height at the prop's x, applies a per-kind scale multiplier, and switches on `kind`.

#### Characters

`drawSurvivor(ctx, engine)` — a from-scratch pixel person:

- Shadow scaled by airborne state.
- If the phase is `dead`, it draws `drawCorpse` instead and returns.
- Picks a pose: **airborne** (tucked legs), **crouching**, **moving** (legs swing with `Math.sin(walkPhase)`), or **idle**.
- Draws backpack + strap, torso with a shaded side, belt, a scarf whose tail sways with `time` and trails further when moving, head with hair, eye, and a scar, and the rear arm.
- `ctx.scale(facing, 1)` mirrors everything for left-facing, so all coordinates are authored right-facing.
- During invulnerability the sprite flickers (`globalAlpha = 0.45` on alternating frames).
- The **front arm and weapon are drawn separately in world space** (`drawWeapon`) so the gun can point at an arbitrary angle rather than following the body flip.

`drawWeapon(ctx, x, y, aim, engine)`:

- Translates to the shoulder, flips if aiming left, rotates by the aim angle, and shifts back by recoil.
- Draws a sleeve + hand, then the weapon shape:
  - **Pipe**: a long bar with highlight/shade rows, plus an arc "swing" overlay while `attackAnim > 0`.
  - **Pistol**: slide, barrel, grip, front sight.
  - **MG**: receiver, barrel, magazine, stock, top rail.
- `muzzleX` is the barrel tip; when `p.muzzle > 0` it paints a bright flash shape whose alpha fades over 55ms.

`drawCorpse` — the player lying down: blood pool, legs, boots, jacket, scarf, head, a single blood fleck.

`drawZombie(ctx, z, time)`:

- Computes `deathT` and the fade alpha; the corpse **squashes** (`scale(facing, 1 - deathT*0.82)`) and shrinks toward the ground instead of falling over — cheap and readable.
- Color branching by type: runner is yellower, brute is darker with a wider torso. A white `flash` palette override happens for 0.14s after any hit.
- Body parts: legs with alternating swing, torso with a dark left edge and a blood stain, head with a dark scalp, two red eyes, a jaw, two forward-reaching arms (raised during the attack wind-up), and rib lines for brutes.
- A pulsing additive eye glow.
- After restoring the transform, a **health pip bar** appears above wounded zombies only — no bars on full-health enemies keeps the screen clean.

`drawPickup` — a bobbing item with a soft glow, a shadow, and per-kind sprite:

- `materials`: a stack of wooden planks.
- `medkit`: white box with a red cross.
- `pistol_ammo` / `mg_ammo`: an olive ammo box with brass stripes.
- Blinks in the last 5 seconds before expiring.

`drawParticles` — for `spark` particles it draws a short line **along the velocity vector** so sparks stretch in the direction of travel; `square`/`smoke` use growing rects. Alpha comes from `life / maxLife`.

`drawBullets` — two passes: a wide, semi-transparent amber glow line, then a 1px bright tracer from `px,py` to `x,y`, plus a head pixel. Drawing from the previous position is what makes fast bullets look continuous.

#### Ambient and overlay

- `drawMotes` — 16 slow drifting dust/firefly motes with sine flicker (called twice: behind and in front of the action).
- `drawReticle` — the crosshair. It is **expanded by recoil** (`spread = 4 + recoil*2`), and turns red when the equipped gun is empty. It is drawn twice (dark offset + colored) so it stays readable over lit windows.
- `drawDamageFlash` — a red full-screen tint on hit, plus a **persistent pulsing red border when health ≤ 30** as a low-health warning.

#### `renderGame` — the draw order

This ordering *is* the visual design. Top to bottom:

```ts
ctx.imageSmoothingEnabled = false          // hard pixel edges
clearRect

drawSky → drawStars → drawMoon → drawClouds
drawRidge(0.08) → drawRidge(0.15) → drawPylons → drawTown
drawHorizonHaze → drawRidge(0.22)
drawDistantTrees(0.44) → drawDistantTrees(0.63)

ctx.save(); ctx.translate(-cam + shakeX, shakeY)   // ← world space begins

  back props  →  mid props (no lamps)  →  drawGround
  lamps + light pools on the ground
  drawMotes
  pickups → zombies → survivor (+weapon) → bullets → particles → float texts
  front props → foreground grass → dark bottom band

ctx.restore()                                       // ← world space ends

drawForegroundLayer (parallax 1.16)
drawMotes
drawDamageFlash
drawReticle
```

Consequences worth noting:

- `front` props are drawn **after the characters**, so a bush can overlap your legs.
- Lamps are drawn *after* the ground because their pole sits on the surface and their glow must land on it.
- The screen shake is applied by translating the whole world layer, but **not** the background or the foreground layer — a subtle cheat that avoids revealing empty edges.
- `reducedMotion` forces `shake = 0`.

### 7.7 `src/game/useGameEngine.ts`

The only bridge between React and the engine. It does four jobs.

**1. Keep one engine instance across renders**

```ts
const engineRef = useRef<GameEngine | null>(null)
if (!engineRef.current) engineRef.current = new GameEngine()
```

A `useRef` (not `useState`) because replacing the engine would reset the game and re-run all effects. Note: `new GameEngine()` runs during render, which is safe because it has no side effects.

**2. Mirror the engine into a React snapshot**

`hud` state starts from `engine.getHud(sound.muted)` and is refreshed inside the rAF loop every ~70ms. Actions call `sync()` right away so button presses feel instant instead of waiting for the next tick.

**3. Expose a typed `actions` object**

`start`, `restart`, `pause`, `resume`, `togglePause`, `toMenu`, `selectWeapon`, `cycleWeapon`, `weld`, `toggleMute`, `setVirtual`. Wrapped in `useMemo` so React children do not re-render needlessly. Each one calls a single engine method and then `sync()`.

`setVirtual(control, pressed)` is how the touch pad works: it writes straight into `engine.input`, unlocking audio on first press, and clears `mouseActive` when you press FIRE (so auto-aim takes over).

**4. Install the loop and all input handlers** (one `useEffect`, cleaned up on unmount)

- **Mouse**: `pointermove`/`pointerdown` convert client coordinates to logical canvas coordinates:
  ```ts
  const rect = canvas.getBoundingClientRect()
  x = ((clientX - rect.left) / rect.width) * VIEW_W
  y = ((clientY - rect.top) / rect.height) * VIEW_H
  ```
  This is essential because the canvas is CSS-scaled; without it, aiming would be wrong at every zoom level. Only `pointerType === 'mouse'` counts as aiming, so touch drags do not hijack the crosshair.
- **Fire merging**: keyboard (`keyFire`) and pointer (`pointerFire`) are OR-ed by `refreshFire()`, so releasing the mouse does not cancel a held `F` key and vice versa.
- **Keyboard**: handles both WASD and arrows, prevents default scrolling for arrows/space, ignores auto-repeat, maps `1/2/3`, `Q`, `H`, `M`, `Esc`/`P`, `Enter`, `R`.
- **Safety**: `blur` and `visibilitychange` reset all inputs and **auto-pause** a running game. Without this, holding `D` and tabbing away would leave the player walking forever.
- **`prefers-reduced-motion`** listener feeds `reducedMotion` into the renderer.
- **Cleanup** removes every listener and cancels the rAF. This is what makes React StrictMode's double-mount in development harmless.
- In dev only, it attaches `window.__deadline`.

### 7.8 `src/game/audio.ts`

A tiny synthesized SFX kit with **no audio files**. One exported singleton: `sound`.

- **`unlock()`** — called from every first user gesture (`start`, pointer down, key press). Browsers block audio until a gesture, so the `AudioContext` is created lazily here. It also builds a 0.7-second **white-noise buffer** once, which every noise-based sound shares.
- **`setMuted` / `muted`** — ramps the master gain to 0 or 0.7 with `setTargetAtTime` (a click-free fade).
- **`noise(duration, filterType, frequency, volume, endFrequency)`** — plays the noise buffer through a `BiquadFilter` whose frequency sweeps down (e.g. `1500 → 400`), with a gain envelope that decays exponentially. This is the "body" of guns, hits, and impacts.
- **`tone(type, duration, frequency, volume, endFrequency, attack)`** — an oscillator with a pitch sweep and a click-free attack/release envelope. This is the "pitch" layer.

Each public sound is just two of those building blocks:

| Sound | Recipe |
|---|---|
| `pistol` | bandpass noise 1500→400 + square 180→60 |
| `mg` | highpass noise 900→1600 + short square 130→70 |
| `melee` | bandpass noise 600→1800 |
| `hit` | lowpass noise + sine 110→60 |
| `kill` | lowpass noise 620→160 + saw 90→40 |
| `hurt` | saw 170→70 + lowpass noise |
| `empty` | short square click |
| `pickup` | two square blips 45ms apart (a "coin" interval) |
| `weld` | bandpass noise + rising triangle |
| `wave` | two long saw sweeps (an ominous horn) |
| `ui` | very short quiet blip |
| `death` | 1.1s saw 140→35 + long lowpass noise |

Because everything is generated, the whole soundtrack is a few hundred bytes of code and starts instantly.

### 7.10 React UI components

#### `src/components/GameCanvas.tsx`

The "stage": a 16:9 (`aspect-video`) box containing the canvas and every overlay layer.

```tsx
const canvasRef = useRef<HTMLCanvasElement>(null)
const { hud, actions } = useGameEngine(canvasRef)
const showHud = hud.phase === 'playing' || hud.phase === 'paused'
```

Structure, bottom to top by `z-index`:

1. `<canvas width={480} height={270}>` — CSS-stretched, `image-rendering: pixelated`, cursor hidden while playing.
2. `.stage-vignette` — CSS radial/linear darkening (z-10).
3. HUD / touch pad / overlay screens (z-20 … z-30), chosen by `hud.phase`.
4. `.scanlines` CRT lines (z-40).
5. Inner shadow.
6. Four tiny amber corner brackets for a "viewfinder" feel.

Everything decorative is `pointer-events-none`; only actual controls are interactive. The canvas also has an `aria-label` and fallback text.

#### `src/components/UIHUD.tsx`

The in-game HUD. Returns `null` in `menu` and `dead` phases.

- `Plate` — a reusable bordered panel with an accent bar and a corner tick, used by all three top panels.
- `Vitals` — "Condition": 10 discrete segments (filled with `Math.ceil` so a sliver of health still shows), color shifts amber → rust → blood as health drops, plus a blinking **CRITICAL** label under 30%. On small screens it also shows distance and wave.
- `Odometer` — distance (`0000 M`), wave, and survived time. Hidden below `lg`.
- `Ledger` — score, materials (plank icon), kills (skull icon), and the ×N multiplier when above 1.
- Toast — top-center, keyed by `hud.toast.id` so it re-animates; border color encodes `tone` (`warn` rust, `good` rot, else bone).
- Bottom-left: `WeaponButton` per weapon — slot number, icon, name (abbreviated to "MG" on narrow screens), ammo (`∞` for the pipe, red when 0), active state with amber border/glow. These are real `<button>`s so keyboard and screen readers work.
- Bottom-right: Weld button (disabled unless `hud.canWeld`, shows the cost), pause/resume toggle, mute toggle.
- A pulsing red vignette overlay when health is ≤30%.

The whole container is `pointer-events-none` with `pointer-events-auto` re-enabled on the two button clusters — so clicks pass through to the canvas to shoot, except on actual buttons.

#### `src/components/OverlayScreens.tsx`

Three full-stage screens plus shared control-list helpers.

- `Keycap` / `ControlRow` / `ControlSheet` — the "Field manual" grid (A D move, SPACE jump, S crouch, LMB fire, 1 2 3 weapons, MOUSE aim, H weld, ESC pause). Reused by the start and pause screens.
- **`StartScreen`** — title `DEADLINE` with a hard drop shadow, tagline, feature tags, the manual, a big `START RUN` button showing the `ENTER` keycap, an audio toggle, and a left-to-right dark gradient so the game world remains visible on the right side behind the menu.
- **`PauseScreen`** — "HOLD THE LINE", a 3-column stat strip (distance/kills/score), the compact manual, Resume / Restart (new terrain) / Abandon run. Shows the run **seed** so a run is reproducible in conversation.
- **`DeathScreen`** — "END OF LINE", a sentence built from your actual stats ("You made it N metres past the last signal. M zombies went down first."), final score, distance/survived/wave, kills/materials/best streak, and Ride Again / Back to platform.

All three use `animate-screen-in` and are scrollable (`overflow-y-auto`) with `.stage-overlay`, which becomes `position: fixed` on phones so the overlay covers the whole viewport instead of only the 16:9 stage.

#### `src/components/TouchControls.tsx`

On-screen gamepad, shown only when `hud.phase === 'playing'`.

- Left cluster: a 3×2 grid with ▲ jump on top, ◀ ▼ ▶ below.
- Right cluster: "Swap gun" (cycles weapons, since there is no room for three buttons), a large FIRE button, and an "Auto aim" caption.
- `HoldButton` uses **pointer events with capture**:
  ```tsx
  onPointerDown → setPointerCapture → setVirtual(control, true)
  onPointerUp / onPointerCancel / onPointerLeave / onLostPointerCapture → false
  ```
  Pointer capture is what makes a finger sliding off a button still release it correctly, and the multiple release handlers cover every browser's edge cases. `touch-none` + `preventDefault` stop the browser from scrolling or showing a context menu.

The container is `.touch-only`, which is `display: none` by default and `display: flex` only under `@media (pointer: coarse)` — so it never appears on desktop.

#### `src/components/Icons.tsx`

Every icon is a tiny inline SVG with `shapeRendering="crispEdges"` made of `<rect>`s: pipe, pistol, MG, planks, skull, speaker (with a `muted` branch), pause, play, crosshair. `currentColor` lets Tailwind text colors drive them. No icon library, no font icons, no network requests.

```
   │   → refreshChunks → waves → death check                   │            │
   │   (mutates: player, zombies[], bullets[], pickups[],       │            │
   │    particles[], texts[], cameraX, score, materials, …)     │            │
   └──────────┬───────────────────────────────┬───────────────┘            │
              │                               │                            │
              ▼ reads (never writes)          ▼ getHud() every ~70ms       │
    renderGame(ctx, engine)             HudState snapshot                 │
      480×270 canvas                       │                             │
      ~60 fps                              ▼                             │
                                    React setHud → UIHUD / OverlayScreens ─┘
                                    (DOM + Tailwind, ~14 fps)     actions call
                                                                 engine methods
```

The arrow back from the UI is the key: **UI → engine is only through `actions`**, and **engine → UI is only through `getHud()`**. There is no shared mutable state between the two, no context, no store library.

## 10. How to add new content

### A new weapon

1. Add the id to `WeaponId` in `types.ts`.
2. Add a `WeaponDef` to `WEAPONS` and add the id to `WEAPON_ORDER` (slot order = array order).
3. Add its starting ammo in `createPlayer()`'s `ammo` object.
4. Add a drawing branch in `render.ts` → `drawWeapon` (and set `muzzleX`).
5. Add an SVG in `Icons.tsx` and a branch in `WeaponIcon`.
6. Add a number key in `useGameEngine.ts` → `onKeyDown` (the `Digit…` cases).
7. If it is melee, set `kind: 'melee'` and `PIPE_RANGE`-style reach logic in `attack()` currently uses `PIPE_RANGE` for every melee weapon — generalize that if the new weapon needs a different reach.

### A new zombie type

1. Add to the `ZombieType` union.
2. Add stats to `ZOMBIE_STATS` (`hp, speed, damage, points, w, h, deathDuration`).
3. Add a probability branch in `pickZombieType()`.
4. Add a color/shape branch in `render.ts` → `drawZombie` (it already branches on `brute` / `runner`).
5. Optionally change its loot in `dropLoot`.

### A new prop

1. Add to `PropKind` in `types.ts`.
2. Add a relative sort weight in `PROP_ORDER` in `world.ts`.
3. Roll for it inside `generateChunk` with a `depth`.
4. Write a `drawX` function in `render.ts` and a `case` in `drawProp` (plus a scale multiplier in the `scale` ternary if needed).

### A new pickup

Add to `PickupKind`, roll it in `dropLoot`, handle it in `collectPickup`, and draw it in `drawPickup`.

## 11. Design notes and quirks

**Deliberate design choices**

- **Analytic terrain, not stored terrain.** This is why "infinite" costs almost nothing: no chunk data is saved, no streaming, no seams.
- **No assets at all.** Every sprite is `fillRect` math; every sound is an oscillator or filtered noise. The whole game is source code.
- **The UI never re-renders per frame.** 60fps simulation, ~14fps React. HUD updates at 70ms are imperceptible for numbers.
- **Fixed timestep + `1 - exp(-k*dt)` easing** = consistent behaviour on any refresh rate.
- **Forgiving platforming**: coyote time, jump buffering, variable jump height, and slope glue.
- **The noise/silence trade-off** is the actual game design: guns are powerful and loud; the pipe is weak and quiet, and crouching shrinks the detection radius from 310px to 120px.
- **Reduced-motion support** is real: shake is disabled and CSS animations are flattened.

**Small quirks you may notice while reading**

- `HudState` exposes a few fields the current UI does not read (`streak`, `weapon`) — they are there for future HUD work (`streak` is the raw combo count; `multiplier` is the derived value).
- `Bullet.fromPlayer` is always `true` and unused by collision — reserved for a future enemy-projectile feature.
- `world.ts` exports `findLamps()` but `render.ts` loops lamps directly; wiring it in would save a pass over chunks.
- The floating score text on a kill shows `+${mult * 100}` when the multiplier is above 1, while the actual score added is `points * mult`. These differ (e.g. a runner at ×2 shows "+200" but adds 320). Intentional-looking shorthand, but worth knowing if you tune scoring.
- The melee side check is `Math.sign(dx) !== dir`, so a zombie at *exactly* the same x (`dx === 0`, sign 0) is skipped unless the aim is horizontal — an edge case that is essentially impossible in practice.
- `updateMenu` contains `p.h = p.onGround ? 30 : p.h`, which is effectively a no-op; harmless leftover.
- Chunks are keyed by index and deleted outside a band, but the map uses the camera position at the time of the call, so the first frame after a `reset()` may briefly hold stale chunk keys — `refreshChunks()` cleans them on the next tick.

**Extending toward more content?** The highest-leverage next steps, in order:

1. A `hits` array or per-weapon reach so melee weapons can differ.
2. A real `save` of best score in `localStorage` (currently everything is in-memory by design).
3. Sprite-sheet or offscreen-canvas caching per prop if you push prop counts much higher.
4. Spatial partitioning of zombies if you raise `ZOMBIE_CAP` well above ~30 (the separation pass is O(n²)).
